# Agent-Uebergabe fuer Pico

## Repository / Projekt

Dieses Repository ist `riederch/pico`.

Pico ist eine local-first Personal AI Companion Foundation. Der aktuelle Fokus liegt auf einer robusten technischen Basis, nicht auf Assistant-Produktfeatures. Die Foundation soll spaeter Memory, Pico Rules, Action Runner, Action History, Tool-Ausfuehrung und weitere Clients tragen.

Das Projekt ist ein pnpm/TypeScript-Monorepo mit unter anderem:

- `apps/core`: Pico Home Core mit REST API, WebSocket, SQLite Event Store, Migration Runner und statischem Web-Serving.
- `apps/web`: frameworkfreier Foundation-Webclient mit HTML, TypeScript und DOM API.
- `packages/protocol`: gemeinsame Protocol-/Event-Typen.
- `packages/sync`: Lamport-/Sync-Grundlagen.
- `docs/protocol`: oeffentliche Protocol-Surfaces und Compatibility Levels.
- `docs/architecture`: Architekturentscheidungen, unter anderem Produktterminologie.

## Aktuelles Ziel

Die Foundation weiter stabilisieren und kleine, architekturkonforme Schritte umsetzen. Keine Produktfeatures vorziehen. Der naechste sinnvolle Arbeitsmodus ist: aktuelle Doku/Konzepte lesen, bestehende APIs nicht brechen, einen klar begrenzten Foundation-Milestone bearbeiten, alle dafuer zusammenhaengenden Aenderungen konsistent nachziehen und danach vollstaendige Qualitaetskontrolle durchfuehren.

## Arbeitsmodus

Vorsichtig arbeiten bedeutet nicht, kuenstlich in sehr kleinen Einzelpatches stehenzubleiben.

Bei eindeutigen technischen Folgeaufgaben soll ein zusammenhaengender, releasefaehiger Milestone fertiggestellt werden, bevor der Arbeitsstand als abgeschlossen gilt. Das ist erlaubt, solange die bestehenden Architektur-, Sicherheits-, Lizenz- und Compatibility-Grenzen eingehalten werden.

Ein Milestone darf mehrere Bereiche gemeinsam anfassen, wenn alle Aenderungen demselben Ziel dienen, zum Beispiel Protocol-Typen, Core-Antworten, Web-Anzeige, Tests und Doku fuer denselben Contract.

Unterbrechen und Rueckfragen stellen ist nur noetig, wenn eine echte Entscheidung offen ist, zum Beispiel:

- mehrere fachlich unterschiedliche Architekturwege sind plausibel,
- ein Security- oder Privacy-Modell waere betroffen,
- ein bestehender oeffentlicher Contract muesste gebrochen werden,
- ein Feature wuerde ueber Foundation-Stabilisierung hinausgehen,
- rechtliche oder kommerzielle Regeln muessten inhaltlich neu festgelegt werden.

Folgefehler aus Build, Tests, Lint, License-, Version- oder Smoke-Gates sollen gezielt behoben werden, bis der Milestone wieder releasefaehig ist.

## Bereits umgesetzt

- `apps/web/index.html`

- `apps/web/src/api.ts`
- `apps/web/src/websocket.ts`

## Getroffene Entscheidungen

- Die Foundation-API bleibt stabil und wird fuer Dashboard- oder interne Verbesserungen nicht erweitert.
- Das Dashboard darf keine neuen Endpunkte voraussetzen.
- Der Webclient bleibt frameworkfrei: HTML, TypeScript, DOM API, CSS ohne Framework.
- Keine Chat-, LLM-, Prompting-, Avatar-, Memory-, Tool-Execution-, Policy-Engine-, Home-Assistant-Control-, Login- oder Benutzerverwaltungsfeatures implementieren.
- Produktterminologie wird im UI und in neuen Namen bevorzugt:
  - Pico Home
  - Pico Vault
  - Pico Surface
  - Pico Relay
  - Pico Rules
  - Action Runner
  - Action History
- Legacy-Begriffe bleiben dort erhalten, wo sie Teil bestehender Protokoll-/Kompatibilitaetsflaechen sind.
- Eventnamen sind oeffentliche Compatibility-Surfaces. Neue oder reservierte Produkt-Eventnamen duerfen nicht stillschweigend Wire-Kompatibilitaet brechen.
- Home Assistant bleibt Einstiegspunkt, aber keine zentrale Kontrollinstanz.
- Der Agent darf lokale Git-Commits erstellen, wenn der Arbeitsstand geprueft ist.
- Push/Pull/Fetch und GitHub-Sync bleiben beim Nutzer ueber PhpStorm.

## Nicht brechen / invarianten

- Assistant macht nur Vorschlaege.
- Pico Rules / Policy Layer entscheidet.
- Action Runner / Executor fuehrt nur freigegebene Aktionen aus.
- Action History / Audit dokumentiert.
- Full Clients besitzen Wissen.
- Light Clients sind reine Interaktionsoberflaechen.
- Relay besitzt keine Autoritaet.
- Keine eigene Kryptographie entwickeln.
- Keine versteckten Automationen.
- Keine Umgehung des Policy Layers.
- Keine produktionsreifen Aussagen solange Features fehlen.
- Home Assistant bleibt Einstiegspunkt, aber niemals zentrale Kontrollinstanz.
- Bestehende Foundation-API nicht veraendern.
- Keine neuen REST-Endpunkte fuer Dashboard-Komfort einfuehren.
- Keine Breaking Changes an JSON-Strukturen.
- Eventmodell, Lamport Clock und Sync-Modell nicht veraendern.
- Reservierte Produkt-/Legacy-Eventtypen duerfen auf `POST /api/events` nicht schreibbar werden.
- `apps/web` bleibt frameworkfrei und ohne neue Runtime-Abhaengigkeiten.
- Keine CLI-Push/Pull/Fetch verwenden; der Nutzer macht GitHub-Sync ueber PhpStorm.
- Lokale Commits durch den Agenten sind erlaubt, aber Push muss durch den Nutzer erfolgen.

## Risiken / Unsicherheiten / Pruefstellen

- Lokaler `main` kann externen Commits hinterherlaufen, weil der Nutzer Push/Pull ueber PhpStorm macht. Vor neuer Arbeit immer `git status --short --branch` und lokale Logs pruefen; bei externen Aenderungen Nutzer ueber PhpStorm synchronisieren lassen.
- `origin/main` kann nach manuellem Push/Pull anders aussehen als der lokale Stand. Keine Annahmen ueber Remote-Status ohne ausdrueckliche Aktualisierung durch den Nutzer.
- Eventtyp-Listen in `packages/protocol` sind nun die zentrale Quelle. Neue Eventnamen muessen dort, in Doku und in Tests konsistent behandelt werden.
- Die Protocol-Tests lesen gezielt Markdown-Codebloecke aus der Doku. Wenn Ueberschriften oder Codeblock-Struktur in den betroffenen Dokumenten geaendert werden, muessen die Test-Helper in `packages/protocol/src/index.test.ts` mit angepasst werden.
- Die Capability-Liste in `packages/protocol/src/index.ts` ist nun ebenfalls zentrale Runtime-Quelle; neue Runtime-Capability-Flags muessen in Doku und Tests konsistent nachgezogen werden.
- Core-Migrationen sind oeffentlich sichtbare Diagnose-Metadaten ueber `GET /api/system/status`; neue Migrationen muessen Core-, Backup- und Doku-Erwartungen konsistent aktualisieren.
- `release:verify` enthaelt inzwischen `license:check`, `version:check`, `build`, `check` und `test`; neue Texte koennen License-, Version- oder Terminologiechecks beeinflussen.
- `version:check` prueft gezielte README-, Add-on-, Workflow-, Runtime- und Protocol-Beispiele. Wenn die Struktur dieser Stellen absichtlich geaendert wird, `scripts/check-version.mjs` mit anpassen.
- Wenn Core statische Webfiles oder Dashboard-Smoke-Tests betroffen sind, muss geprueft werden, ob `apps/web/dist` aktuell gebaut wird und ob Core die erwarteten Assets ausliefert.
- Es gibt keine Compatibility Claims ohne passende Conformance Tests. Doku zu `L0` bis `L5` beachten.
- `apps/web/src/render.test.ts` ist ein struktureller Smoke-Test fuer die Header-/Renderer-Ausrichtung, kein vollstaendiger DOM-Interaction-Test.

## Naechste Schritte

1. Vor weiterer Arbeit `git status --short --branch` und die lokalen Logs pruefen.
2. Falls externe Commits eingegangen sind: Nutzer ueber PhpStorm pullen lassen, danach lokale Doku und `git log`/`git status` lesen.
3. Falls dieser Arbeitsstand uebernommen werden soll: Agent darf lokal committen, aber nicht per CLI pushen. Push muss der Nutzer ueber PhpStorm ausfuehren.
4. Einen klar begrenzten, releasefaehigen Foundation-Milestone bearbeiten und bis zum gruenen Ergebnis fertigstellen, solange keine echte Entscheidung offen ist.
5. Sinnvolle Kandidaten:
   - Internen Read-Helper fuer `pico_home_claim_state` ergaenzen, weiterhin ohne oeffentliche Schreib-API.
   - Protocol-/Core-Kontrakte weiter deduplizieren und testen.
   - Dashboard-Smoke-Abdeckung nur dort erweitern, wo sie bestehende Foundation-Oberflaechen prueft, ohne neue Produktfeatures einzufuehren.
   - Doku und Tests fuer reservierte Eventnamen/Compatibility Levels konsistent halten.
6. Nach jeder Codeaenderung mindestens die betroffenen Paketchecks ausfuehren, vor Commit immer:
   - `pnpm build`
   - `pnpm test`
   - `pnpm release:verify`
7. Nur lokal committen, wenn alles gruen ist. Push bleibt beim Nutzer ueber PhpStorm.
