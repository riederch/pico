# Agent-Uebergabe fuer Pico

## Repository / Projekt

Dieses Repository ist `riederch/pico`.

Pico ist eine local-first Personal AI Companion Foundation. Der aktuelle Fokus liegt auf einer robusten technischen Basis, nicht auf Assistant-Produktfeatures. Die Foundation soll spaeter Memory, Pico Rules, Action Runner, Action History, Tool-Ausfuehrung, Pico Link, Pico Home Link und weitere Clients tragen.

Das Projekt ist ein pnpm/TypeScript-Monorepo mit unter anderem:

- `apps/core`: Pico Home Core mit REST API, WebSocket, SQLite Event Store, Migration Runner und statischem Web-Serving.
- `apps/web`: frameworkfreier Foundation-Webclient mit HTML, TypeScript und DOM API.
- `packages/protocol`: gemeinsame Protocol-/Event-Typen.
- `packages/sync`: Lamport-/Sync-Grundlagen.
- `docs/protocol`: oeffentliche Protocol-Surfaces und Compatibility Levels.
- `docs/architecture`: Architekturentscheidungen, Produktterminologie, Host-/Setup-Konzepte und Transport-/Relay-Konzepte.
- `pico_core`: Home Assistant Add-on Packaging fuer Pico Core.

## Aktuelles Ziel

Die Foundation weiter stabilisieren und architekturkonforme, klar begrenzte Milestones umsetzen. Keine Produktfeatures vorziehen. Der sinnvolle Arbeitsmodus ist: aktuelle Doku/Konzepte lesen, bestehende APIs nicht brechen, einen klar begrenzten Foundation-Milestone bearbeiten, alle dafuer zusammenhaengenden Aenderungen konsistent nachziehen und danach vollstaendige Qualitaetskontrolle durchfuehren.

## Arbeitsmodus

Vorsichtig arbeiten bedeutet nicht, kuenstlich in sehr kleinen Einzelpatches stehenzubleiben.

Bei eindeutigen technischen Folgeaufgaben soll ein zusammenhaengender, releasefaehiger Milestone fertiggestellt werden, bevor der Arbeitsstand als abgeschlossen gilt. Das ist erlaubt, solange die bestehenden Architektur-, Sicherheits-, Lizenz- und Compatibility-Grenzen eingehalten werden.

Ein Milestone darf mehrere Bereiche gemeinsam anfassen, wenn alle Aenderungen demselben Ziel dienen, zum Beispiel Protocol-Typen, Core-Antworten, Web-Anzeige, Tests und Doku fuer denselben Contract.

Unterbrechen und Rueckfragen stellen ist nur noetig, wenn eine echte Entscheidung offen ist, zum Beispiel:

- mehrere fachlich unterschiedliche Architekturwege sind plausibel,
- ein Security- oder Privacy-Modell waere betroffen,
- ein bestehender oeffentlicher Contract muesste gebrochen werden,
- ein Feature wuerde ueber Foundation-Stabilisierung hinausgehen,
- rechtliche oder kommerzielle Regeln muessten inhaltlich neu festgelegt werden.

Folgefehler aus Build, Tests, Lint, License-, Version- oder Smoke-Gates sollen gezielt behoben werden, bis der Milestone wieder releasefaehig ist.

Der Konzept-Milestone `docs: define dedicated Pico Home image setup` wurde umgesetzt:

- Neue ADR `docs/architecture/0027-dedicated-pico-home-image-and-first-boot-setup.md` wurde angelegt.
- Sie macht `Pico Home Image` als zukuenftigen offiziellen Installationspfad neben Home Assistant Add-on, Container, NAS/Mini-Server und lokalem Service explizit.
- `Dedicated Pico Home` ist dort als lokales Geraet definiert, das mit dem Pico Home Image bootet und als Pico Home Host dient.
- Der First-Boot-Flow ist konzeptioniert:
  - Image flashen,
  - Geraet bootet,
  - Pico Home startet automatisch,
  - Host ist `unclaimed`,
  - Setup Mode zeigt Move-In Code ueber lokalen/protected Kanal,
  - Pico Vault claimed das Empty Pico Home,
  - erster Pico wird Home Host Pico,
  - Move-In Code wird invalidiert,
  - Setup Mode endet,
  - Host wird `claimed`.
- Die ADR stellt klar: Move-In Code ist kein Master Key, kein Encryption Key, kein Recovery Secret und keine Auth-Abkuerzung.
- Eine spaetere Claim-API ist nur als Teil eines sauberen Setup-Mode-/Bootstrap-Security-Modells akzeptabel, nicht als dauerhaft offene Komfort-Schreib-API.
- Die ADR verlangt vor einer Implementierung Details zu Code-Expiry, Display-Kanal, Replay-Schutz, Rate-Limits, Host-Identity-Persistenz, Reset/Recovery, Audit und Protocol/Capability-Kompatibilitaet.

In diesem Arbeitsstand wurde der Konzept-Milestone `docs: define Pico Link transport facade and relay network` umgesetzt:

- Neue ADR `docs/architecture/0028-pico-link-transport-facade-and-relay-network.md` wurde angelegt.
- Sie definiert Pico Home als lokalen Endknoten im Pico-Relay-/Transportnetz, nicht als direkt oeffentlich erreichbaren Server.
- Remote-Erreichbarkeit fuer Pico Home laeuft konzeptionell ueber Pico Link Transports, primaer Pico Relay, nicht ueber Portforwarding oder public inbound Pico Home APIs.
- Pico Relay ist Transport/Weiterleitung/Queue/Deduplikation, aber keine Autoritaet, kein Identity Owner, kein Action Authorizer und kein Klartext-Leser.
- Pico Link bleibt transportneutral: konkrete Transporte laufen hinter einer Transport Facade.
- Transport Adapter koennen Relay, LAN/direct, VPN/direct, WebSocket, spaeter QUIC/WebRTC, Meshtastic oder andere Funk-/Low-Bandwidth-Standards sein.
- Meshtastic wurde als optionaler Low-Bandwidth-Transport eingeplant, aber nur fuer kleine verschluesselte Pico-Link-Pakete wie Presence, Notfall-Kurznachrichten, Wake-up-Hints oder kleine Store-and-Forward-Pakete.
- Meshtastic-spezifische Details gehoeren in einen Meshtastic Transport Adapter und duerfen nicht zu Pico-Identitaet, Pico-Verschluesselung oder Pico-Autoritaet werden.
- Die ADR haelt fest, dass befreundete Picos auch ueber unterschiedliche Pico Homes hinweg kommunizieren koennen; Homes begrenzen Hosting und Haushaltskontext, nicht Beziehungen zwischen Picos.
- Die ADR verankert die kryptographische Grenze: asymmetrische Pico-/Home-/Device-Identitaetskeys, Signaturen und Ende-zu-Ende-verschluesselte Pico-Link-Payloads sind Architekturgrundlage; PGP ist eine Analogie, aber nicht automatisch das Wire-Protokoll.

## Getroffene Entscheidungen

- Die Foundation-API bleibt stabil und wird fuer Dashboard- oder interne Verbesserungen nicht unnoetig erweitert.
- Das Dashboard darf keine neuen Endpunkte voraussetzen.
- Der Webclient bleibt frameworkfrei: HTML, TypeScript, DOM API, CSS ohne Framework.
- Keine Chat-, LLM-, Prompting-, Avatar-, Memory-, Tool-Execution-, Policy-Engine-, Home-Assistant-Control-, Login- oder Benutzerverwaltungsfeatures implementieren.
- Produktterminologie wird im UI und in neuen Namen bevorzugt:
  - Pico Home
  - Empty Pico Home
  - Move-In Code
  - Home Host Pico
  - Home Member Pico
  - Pico Vault
  - Pico Surface
  - Pico Relay
  - Pico Link
  - Pico Home Link
  - Pico Rules
  - Action Runner
  - Action History
- Legacy-Begriffe bleiben dort erhalten, wo sie Teil bestehender Protokoll-/Kompatibilitaetsflaechen sind.
- Eventnamen sind oeffentliche Compatibility-Surfaces. Neue oder reservierte Produkt-Eventnamen duerfen nicht stillschweigend Wire-Kompatibilitaet brechen.
- Home Assistant bleibt Einstiegspunkt, aber keine zentrale Kontrollinstanz.
- Home Assistant Add-on, Container und spaeteres Pico Home Image muessen demselben Host-/Tenancy-/Move-In-Modell folgen.
- Dedicated Pico Home Image ist ein zukuenftiger Installationspfad, keine separate Autoritaetsform.
- Eine Claim-Schreib-API darf erst entstehen, wenn Setup Mode, Move-In-Code-Sicherheit, Host Admin Membership, Audit und Auth-/Bootstrap-Grenzen sauber definiert sind.
- Pico Home wird fuer Remote-Erreichbarkeit als Endknoten im Pico-Link-/Relay-Netz betrachtet, nicht als public HTTP server.
- Remote-Zugriff auf Pico Home erfolgt produktkonzeptionell ueber Pico Link Transports, primaer Pico Relay; Portforwarding auf die Foundation-API ist kein Zielmodell.
- Pico Relay und Transport Adapter sind Transport, nicht Autoritaet. Sie duerfen verschluesselte Pakete routen/queueen/deduplizieren, aber nicht entschluesseln, autorisieren oder Identitaeten besitzen.
- Pico Link bleibt transportneutral. Meshtastic und andere Funkstandards duerfen nur als Adapter hinter einer Facade eingeplant werden.
- Picos koennen ueber unterschiedliche Homes hinweg kommunizieren; Beziehungen gehoeren den Picos, nicht den Homes.
- Pico braucht asymmetrische Kryptographie als Identitaets-/Ausweis-/Signaturgrundlage; keine eigene Kryptographie erfinden.
- Der Agent darf lokale Git-Commits erstellen, wenn der Arbeitsstand geprueft ist.
- Push/Pull/Fetch und GitHub-Sync bleiben beim Nutzer ueber PhpStorm.

- Action History / Audit dokumentiert.

- Light Clients / Pico Surfaces sind reine Interaktionsoberflaechen.
- Relay besitzt keine Autoritaet.
- Keine eigene Kryptographie entwickeln.
- Keine versteckten Automationen.
- Keine Umgehung des Policy Layers.
- Keine produktionsreifen Aussagen solange Features fehlen.
- Home Assistant bleibt Einstiegspunkt, aber niemals zentrale Kontrollinstanz.
- Dedicated Pico Home Image ist ein Packaging-/Installation-Pfad, kein neues Trust-Modell.
- Bestehende Foundation-API nicht brechen.
- Keine neuen REST-Endpunkte fuer Dashboard-Komfort einfuehren.
- Keine Breaking Changes an JSON-Strukturen.
- Eventmodell, Lamport Clock und Sync-Modell nicht veraendern.
- Reservierte Produkt-/Legacy-Eventtypen duerfen auf `POST /api/events` nicht schreibbar werden.
- `apps/web` bleibt frameworkfrei und ohne neue Runtime-Abhaengigkeiten.
- Keine Claim-Schreib-API, kein Move-In-Code-Endpoint und kein Setup Mode ohne eigenes Security-/Bootstrap-Konzept implementieren.
- Pico Home nicht als public HTTP server modellieren; Remote-Erreichbarkeit laeuft ueber Pico Link / Relay.

- Keine CLI-Push/Pull/Fetch verwenden; der Nutzer macht GitHub-Sync ueber PhpStorm.
- Lokale Commits durch den Agenten sind erlaubt, aber Push muss durch den Nutzer erfolgen.

## Risiken / Unsicherheiten / Pruefstellen

- Lokaler `main` kann externen Commits hinterherlaufen, weil der Nutzer Push/Pull ueber PhpStorm macht. Vor neuer Arbeit immer `git status --short --branch` und lokale Logs pruefen; bei externen Aenderungen Nutzer ueber PhpStorm synchronisieren lassen.
- `origin/main` kann nach manuellem Push/Pull anders aussehen als der lokale Stand. Keine Annahmen ueber Remote-Status ohne ausdrueckliche Aktualisierung durch den Nutzer.
- Eventtyp-Listen in `packages/protocol` sind die zentrale Quelle. Neue Eventnamen muessen dort, in Doku und in Tests konsistent behandelt werden.
- Die Protocol-Tests lesen gezielt Markdown-Codebloecke aus der Doku. Wenn Ueberschriften oder Codeblock-Struktur in den betroffenen Dokumenten geaendert werden, muessen die Test-Helper in `packages/protocol/src/index.test.ts` mit angepasst werden.
- Die Capability-Liste in `packages/protocol/src/index.ts` ist zentrale Runtime-Quelle; neue Runtime-Capability-Flags muessen in Doku und Tests konsistent nachgezogen werden.
- Core-Migrationen sind oeffentlich sichtbare Diagnose-Metadaten ueber `GET /api/system/status`; neue Migrationen muessen Core-, Backup- und Doku-Erwartungen konsistent aktualisieren.
- `release:verify` enthaelt `license:check`, `version:check`, `build`, `check` und `test`; neue Texte koennen License-, Version- oder Terminologiechecks beeinflussen.
- `version:check` prueft gezielte README-, Add-on-, Workflow-, Runtime- und Protocol-Beispiele. Wenn die Struktur dieser Stellen absichtlich geaendert wird, `scripts/check-version.mjs` mit anpassen.
- Wenn Core statische Webfiles oder Dashboard-Smoke-Tests betroffen sind, muss geprueft werden, ob `apps/web/dist` aktuell gebaut wird und ob Core die erwarteten Assets ausliefert.
- Es gibt keine Compatibility Claims ohne passende Conformance Tests. Doku zu `L0` bis `L5` beachten.
- `apps/web/src/render.test.ts` ist ein struktureller Smoke-Test fuer die Header-/Renderer-Ausrichtung, kein vollstaendiger DOM-Interaction-Test.
- ADR 0027 definiert das Dedicated-Pico-Home-Image nur konzeptionell. Keine Implementierung daraus ableiten, ohne Setup-Mode-/Security-Details zuerst zu klaeren.
- ADR 0028 definiert Relay, Transport Facade, Meshtastic/future radio transports und Inter-Pico-Kommunikation nur konzeptionell. Keine Relay-/Transport-/Crypto-Implementierung daraus ableiten, ohne separate Security-, Crypto- und Protocol-Milestones.
- Metadata-Privacy beim Relay ist offen: auch verschluesselte Pakete koennen Zeit, Groesse, Routing-Hints und Beziehungsmuster leaken. Spaeter separat behandeln.
- Low-Bandwidth-Transporte brauchen harte Paketklassen, Payload-Limits, Rate-Limits, Fragmentierungsgrenzen und klare Ausschluesse fuer Memory/File/LLM-Sync.

## Naechste Schritte

2. Falls externe Commits eingegangen sind: Nutzer ueber PhpStorm pullen lassen, danach lokale Doku und `git log`/`git status` lesen.

   - Weiterer Pico-Home-Tenancy-Ausbau erst mit eigenem Security-/Bootstrap-Modell; keine Claim-Schreib-API als Komfortabkuerzung einfuehren.
