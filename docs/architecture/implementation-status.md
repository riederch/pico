# ADR implementation status

This matrix separates ADR decision status from implementation status. An `Accepted` ADR may still be concept-only, reserved, partially implemented or blocked before production.

Pico is currently foundation-stage. This document does not make Pico Home, Pico Link, Relay, Crypto, Membership, Pico Rules, Action Runner, Action History, Memory Store or Home Assistant control production-ready.

## Scope

This matrix tracks every numbered ADR file currently present under `docs/architecture/`, with extra attention on production-blocking, security-sensitive and compatibility-sensitive decisions.

If older ADR files are added later, they should be added here before their decision status is treated as an implementation claim.

## Status categories

| Category | Meaning |
|---|---|
| implemented | The described behavior is present in the current codebase for the stated scope. |
| partially implemented | A limited skeleton or hardening subset exists, but major required behavior is missing. |
| concept-only | The ADR is accepted direction only; no meaningful runtime implementation exists. |
| reserved | Names, types or capability direction exist, but the runtime write path or product behavior is not implemented. |
| blocked-before-production | The ADR defines prerequisites that must be satisfied before production or public compatibility claims. |
| informational | The ADR is planning, product direction or explanatory context rather than a discrete runtime feature. |
| superseded | The ADR has been replaced by a later ADR and should not be used as current implementation direction. |

The counter witnesses the anchor's generation rather than storing it: each write bumps it and the document records the value it was written at, so a document restored from an earlier generation carries a value the platform has already passed. The document is written before the counter is bumped, so a crash between the two leaves it one generation ahead - safe, and matching the anchor's existing rule that being ahead costs one re-initiation while being behind resurrects a spent authorization; the exact residual is that within that window a one-generation rollback reads as the crash. The tpm2 adapter is verified against a software TPM - same tools, same NV semantics - because defining an NV index consumes limited persistent storage on real hardware; those tests skip visibly where the tools are absent. Not shown: behaviour against physical TPM hardware, which belongs to the image. IM1 itself cannot close while there is no image, and IM2 (encrypted or absent swap) and IM3 (verifying updater) are properties of an image build rather than of this tree.
