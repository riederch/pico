# 0156 - A relay account should be a key it proves, not a secret it was handed

## Status

**Draft sketch, 2026-08-20. Nothing here is accepted and nothing is built.**
AK1-AK8 are proposed gate shapes rather than decided ones, and the sketch
exists to be argued with. No status matrix row, no `.agent-context.md` entry,
no ADR 0128 status note on anything it touches - those follow acceptance, not
drafting, and ADR 0146 set that precedent.

Written from a user question while bringing up the first real relay under a
Supervisor (ADR 0155): the relay was about to be published through a Cloudflare
tunnel, the question was whether HTTP behind TLS means the payload is encrypted
twice, and the question after that was **whether the account credential could
be replaced by an asymmetric scheme**.

The first question has an answer that needs no ADR: the payload is sealed end
to end by ADR 0107 and travels through a relay unread, so the transport layer
protects the *envelope* and not the content. The second question does not have
an answer in the tree, and it points at a property ADR 0149 decided
deliberately rather than by default. That is what this sketch is about.

## Context

**What exists today, and it is not an accident.** A relay account is 128
uniform random bits, lowercase hex, generated by the relay when an operator
issues an account (`link-relay-operator.ts:44`, ADR 0154 RO3). It arrives in
`x-pico-relay-account` on the four routes that act on somebody's mailboxes -
`register`, `collect`, `acknowledge`, `deregister` - and `deliver` carries none,
because a stranger delivering into a mailbox must not need an account
(`link-relay-client/src/index.ts:88-152`, ADR 0149 RS3).

Three things about it are better than they look:

- **The relay keeps a digest, not the credential.** `picoRelayCredentialDigest`
  is a plain SHA-256, and `operator-claim.ts:71-75` explains why plain is the
  right primitive here rather than a lazy one: the input is 128 uniform random
  bits this process generated, so there is no dictionary to attack. A stolen
  relay database yields nothing that opens an account.
- **Ownership is enforced in the store, not at the route.** `collect` and
  `acknowledge` compare the mailbox's `accountDigest` against the presented
  credential's digest and answer `mailbox_not_yours` for three different states
  - not yours, not there, and revoked - so there is no oracle
  (`apps/relay/src/store.ts:529-552`, ADR 0154 RO5).
- **Revocation ends the mailboxes with the account.** The first version forgot
  that and left senders delivering into addresses nobody could ever collect
  from, with both sides believing the exchange had succeeded
  (`store.ts:277-295`).

**The seam.** The credential is a bearer token. It exists in three places it
could leak from that a key would not have: it is generated by the relay and
must travel to the Home once at issuance, it travels again on every
account-bearing request, and it sits in the Home's deployment configuration as
`PICO_LINK_RELAY_ACCOUNT_ID`. Anybody who captures it - from a log, a
screenshot, a support conversation, a terminating proxy, or the wire - can
collect and acknowledge that account's mailboxes until somebody revokes it.
Nothing in the exchange proves freshness, so a captured request replays.

TLS closes the wire half of that, and the deployment that raised the question
has it. TLS does not close the other two halves, and it introduces a party -
the tunnel's edge terminates TLS, so the envelope and the credential are
cleartext there.

**The argument against this sketch is already written down, which is why the
sketch is worth writing.** `link-relay-operator.ts:12`:

> Everything here is a bearer credential and a number. No identity, no
> delegation, no signature: ADR 0149 RS2 is a property of the whole process,
> not of one file, and administration is exactly where it would have been
> convenient to break it.

And RS2 is not prose. `scripts/check-relay-boundary.mjs` refuses the vocabulary
that would mean the relay had learned a Pico - `picoIdentity`, `delegation`,
`membership`, `crypto_sign`, `signatureHex` - matched against code with
comments stripped, so the paragraph explaining the rule cannot trip the check
enforcing it. Its stated reason is the sharpest objection this sketch faces:

> A signature check would have been the reflex - it answers "who", and the
> relay's only question is "is this within somebody's quota".

Any version of this proposal has to answer that, and "the key is not an
identity" is a thinner answer than it first sounds. An absence that is checked
is worth more than an absence that is intended, and the way checked absences
die is by acquiring one reasonable exception.

## Scope

**The account credential only.** The operator credential (ADR 0154 RO1) has the
same shape and the same one-shot issuance, but it lives on a loopback listener
by default and its exposure is a deliberate second act. If this is accepted, it
is the obvious follow-on and it is not decided here.

Out of scope: the payload, which ADR 0107 already seals; delivery, which takes
no credential and must keep taking none; and anything about who a Pico is,
which is the thing a relay must never learn.

## The sketch

**An account is a key pair the Home holds, and the relay knows only its public
half.**

`accountCreate` stops generating a secret. It takes a public key, records it
beside the quota row it already keeps, and returns the same non-secret
`accountRef` it returns today. The relay never holds anything that could act as
the account, at any point in its life - not at issuance, not in the database,
not in a backup of the database.

The four account-bearing routes stop carrying `x-pico-relay-account` and carry
a signature over a canonical statement of the request instead:

```
canonicalJson({ route, mailbox, <route's own fields>, freshness })
```

`canonicalJson` already exists for exactly this purpose
(`packages/protocol/src/canonical-transport.ts`, ADR 0034), and was extracted
because three separate copies of a canonical encoding are three spellings of
the same bytes waiting to disagree.

**The prior art is in the tree and it argues for this.**
`packages/protocol/src/device-enrolment.ts:34` describes its own shape as
"public keys, one activation to sign, and one signature - **never a secret that
could be replayed** into a second". That is the same sentence this sketch would
write about a relay account.

**The gain is not primarily on the wire.** TLS already covers the wire where
somebody deploys it. The gain is that a secret which never exists cannot be
found later: not in the boot log that prints an issuance, not in the Home's
options, not in a backup, not at a terminating proxy, and not in the support
conversation where somebody pastes their configuration.

## Gates, proposed

- **AK1 - The relay holds a public key and nothing that could act as one.** No
  credential at issuance, none at rest, none in a database backup. The check is
  the same class as RS2's: an absence, measured against code.

- **AK2 - The credential never travels, not once.** Today's issuance hands a
  secret from the relay to the Home. Under this sketch the key pair is
  generated in the Home and only its public half moves. If any version of the
  design has the relay generate a private key "for convenience", that version
  has kept the whole problem and added mathematics.

- **AK3 - A signed statement carries a closed field list, and an unknown field
  is a refusal.** `parsePicoLinkPacket` already refuses an unknown key outright
  (ADR 0147 RY1), for the reason that an operator cannot ask for priority if a
  packet carrying priority is not a packet. The same construction here is what
  keeps a signature from growing a field that names a person.

- **AK4 - Replay has a stated window and a stated cost.** Either a freshness
  value on a grid, with the window written down, or a nonce the relay
  remembers, with its retention and its size bound written down. Not "a
  timestamp" with the question left open. Note that ADR 0147's reason for
  rounding `expiresAt` - not leaking the sender's clock - does *not* apply
  here: the four signed routes are exactly the ones where the caller is already
  known to the relay, so a precise time tells the operator nothing new.

- **AK5 - RS2 stays mechanical.** `check-relay-boundary.mjs` must not gain an
  exception. If a verification path is admitted, the check has to be narrowed
  by construction rather than by exemption: the relay may verify against a key
  it recorded at account creation and over a statement whose fields the relay
  itself defined, and nothing else. A gate that says "no signature except this
  one" is a gate that will say it twice.

- **AK6 - Delivery is untouched.** `deliver` takes no credential today
  (ADR 0149 RS3) and takes none after. A stranger must be able to put a packet
  in a mailbox they were handed, and the mailbox's 128 bits are the capability.

- **AK7 - An account survives a restore, or the release says it does not.**
  Today the account identifier lives in deployment configuration and comes back
  with the machine. A private key would live where keys live, and keys are
  deliberately **excluded from backups** (ADR 0072 R6, ADR 0080 H5), so a
  restored Home would hold no account and would have to be re-claimed. That is a
  real regression in operability. It is affordable only if the changelog states
  the repair step before anybody installs it, per
  `docs/release/upgrade-contract.md`.

- **AK8 - Both shapes coexist for one dated transition, and the end is part of
  the decision.** New wire semantics raise `picoProtocolVersion`
  (`docs/release/versioning.md`). A relay that accepts a bearer credential
  forever has not replaced anything; it has added an alternative, and the
  weaker one decides the security of the pair.

## What this would cost

Named here rather than in Residuals, because a sketch whose costs live in a
footnote is a sketch arguing for itself.

**An exposed port would do more work per request.** ADR 0154 RO9 bounds "the
work an unauthenticated caller can make the relay do" and counts it honestly as
"a digest and a query per request, small each and unbounded in aggregate". A
signature verification is orders of magnitude more than a digest, on a port
whose whole purpose is to be reachable by strangers. The bucket exists and
would still hold, but the quantity it bounds gets more expensive, and that is a
change to the reasoning behind an accepted gate rather than a detail of this
one.

**Key custody arrives where there was none.** The relay client currently needs
a string from configuration. It would need access to a private key, which means
the vault or the keystore, which means this touches ADR 0081 and the whole
custody argument - for a component whose merit today is that it holds nothing.

**Freshness is state in something deliberately stateless about callers.** The
relay counts tokens globally rather than per caller, on the stated grounds that
a relay behind a reverse proxy sees one address for everybody and the header
that would say otherwise is one nobody signed (`apps/relay/src/rate-limit.ts`).
A nonce cache is per-caller state in exactly that component.

**The absence gets an exception, or it gets a narrower definition.** This is the
real price, and AK5 is the attempt to pay it. If the narrowing cannot be
written as a check, the honest outcome of this sketch is rejection.

## Rejected alternatives

### An HMAC over the request, using the credential that already exists

Removes the bearer from the wire without any asymmetric machinery, and looks
like the cheap version of this proposal. It is worse where it counts: to verify
an HMAC the relay must hold the actual secret, not a digest of it. Today a
stolen relay database opens nothing. Under HMAC the verifier is also a forger,
so the relay would go from holding nothing usable to holding every customer's
key. Better on the wire, worse at rest, and at rest is the half TLS does not
already cover.

### Reuse the Home's host identity key

The Home already has one (ADR 0080), and signing with it would need no new key
material. It is exactly what RS2 forbids: the relay would hold a value that is
a Pico identity, and ADR 0031's prohibition on relay account identity being
equivalent to Pico identity would be broken by the shortest possible path. An
account key must be relay-specific, meaningless outside that relationship, and
rotatable without touching anything a person is.

### Mutual TLS

Moves the problem into the deployment and looks free. It fails in the
deployment that raised the question: a tunnel terminates TLS at its edge, so
the relay never sees a client certificate, and the header that would report one
is one nobody signed. It would also make the security of an account depend on
how the operator publishes the port, which is the opposite of ADR 0104's
division - a person's security should not be a deployment parameter.

### Do nothing, and rely on TLS

The status quo, and it is not unreasonable. Bearer over TLS is what most APIs
do, the credential is 128 uniform random bits, the relay stores only a digest,
and revocation works and ends the mailboxes with it. If this sketch is
rejected, the honest form of the rejection is a line in the relay's
documentation saying that the account credential is a bearer secret, that
publishing a relay without TLS exposes it, and that a captured one is valid
until revoked. Today no document says that, which is the one thing that should
change whatever is decided.

## Questions this sketch does not decide

- Which suite. Pico names suites explicitly (`picoIdentitySuite`,
  `picoShareSuite`), and a relay account suite would be another - or would
  deliberately not be, if the point is that a relay account is not identity
  material.
- Whether the operator credential follows, and whether it should follow
  *first*, since it is the one that unlocks account creation.
- Rotation without re-claiming: whether a Home can present a new public key
  under an existing account, and what happens to that account's open mailboxes
  if it can.
- Whether `accountRef` stays the first bytes of a digest when there is no
  credential digest to take it from.
- Whether any of this is worth doing before a second person runs a relay.

## Relationship to other ADRs

- **ADR 0149 RS2** is the property this would narrow, and `check-relay-boundary.mjs`
  is where the narrowing has to be expressible or the sketch fails.
- **ADR 0031** forbids relay account identity being equivalent to Pico identity;
  AK1 and the rejection of the host identity key are that applied.
- **ADR 0154** issues accounts and revokes them; AK2 changes what issuance
  hands over and RO5's revocation semantics are unaffected.
- **ADR 0147 RY1** is the construction AK3 copies: a closed field list enforced
  by refusal rather than by policy.
- **ADR 0034** decided canonicalization and signature inputs; this reuses them
  rather than inventing a second spelling.
- **ADR 0072 R6 / ADR 0080 H5** exclude keys from backups, which is what makes
  AK7 a real cost rather than a formality.
- **ADR 0104** is why mutual TLS is rejected: what protects a person is not a
  deployment parameter.
- **ADR 0155** is the deployment that raised the question.
- **ADR 0157** is the sibling sketch, and its LR5 is where the two meet: a
  relay reached over a LAN URL has no TLS in front of it, so the deployment
  that sketch enables is the one a transmitted secret is worst in.
